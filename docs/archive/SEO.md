# SEO.md — معماری سئو فروشگاه علی حان

> این سند **همراه** `ARCHITECTURE.md` است و جایگزین آن نیست. Claude Code باید هر دو را بخواند.
> هر جا این سند با `ARCHITECTURE.md` تعارض داشت، **در موضوعات سئو این سند مقدم است** و تغییر باید در بخش «تصمیمات تکمیلی» `ARCHITECTURE.md` هم ثبت شود.
>
> فایل متن محصولات در `docs/product-details.md` قرار دارد. **متن توضیحات** محصولات از آن فایل گرفته می‌شود، ولی **فیلدهای سئو (عنوان، متا، نامک، کلمه کلیدی)** از جدول بخش ۲ همین سند — جدول این سند اصلاح‌شده و مرجع نهایی است.

## 0. قوانین کار برای Claude Code

1. کارهای سئو در **فازهای S0 تا S5** (بخش ۱۳) آمده و هرکدام به یک فاز `ARCHITECTURE.md` متصل است. همان قوانین فازبندی `ARCHITECTURE.md` (یک فاز در هر زمان، typecheck/lint/build، commit، توقف و گزارش) اینجا هم برقرار است.
2. **اگر فاز مرتبط در `ARCHITECTURE.md` قبلاً انجام شده**، کار سئوی آن را به‌صورت یک migration/تغییر جدا اضافه کن؛ فاز قبلی را بازنویسی نکن.
3. تمام منطق سئو در `src/lib/seo/` متمرکز است. هیچ تگ متا، JSON-LD یا canonical به‌صورت دستی و پراکنده در صفحات نوشته نشود — فقط از builderهای این پوشه.
4. توابع `src/lib/seo/` **خالص و تست‌پذیر** باشند و تست واحد داشته باشند.
5. 🔴 **هیچ داده‌ی ساختگی** در structured data قرار نگیرد: نه امتیاز، نه تعداد نظر، نه نظر مشتری، نه موجودی. (بخش ۷.۴)
6. متن‌هایی که حاوی ادعای واقعی کسب‌وکار هستند (سابقه، ماندگاری محصول، مناطق ارسال، زمان ارسال) را **از خودت نساز**. جای آن‌ها `{{تکمیل توسط علی حان: ...}}` بگذار و در گزارش فاز فهرستشان کن.

## 1. اهداف و استراتژی کلمات کلیدی

### ۱.۱ اهداف
| هدف | صفحه‌ی هدف |
|---|---|
| رتبه برای «خرید باقلوا»، «باقلوای ترکی»، «خرید باقلوای ترکی»، «خرید آنلاین باقلوا» | صفحه‌ی اصلی |
| رتبه برای نام دقیق هر محصول با/بدون «خرید» (مثل «خرید باقلوا گردویی»، «سوتلاوا») | صفحه‌ی همان محصول |
| رتبه برای «خرید هاویج» / «شیرینی هاویج» | صفحه‌ی دسته‌ی هاویج (hub) |
| رتبه برای «شیرینی ترکی» / «دسر ترکی» | دسته‌ی دسرهای ترکی |
| رتبه‌ی محلی (شیرینی‌فروشی ترکی + نام منطقه) | صفحه‌ی هر شعبه |

### ۱.۲ قاعده‌ی طلایی: یک نیت جستجو = یک URL
اگر دو صفحه برای یک عبارت بهینه شوند، با هم رقابت می‌کنند (cannibalization) و هیچ‌کدام خوب رتبه نمی‌گیرند. بنابراین:
- هر عبارت کلیدی اصلی فقط در **یک** صفحه به‌عنوان `focusKeyword` تعریف می‌شود.
- پنل ادمین هنگام تکرار `focusKeyword` در محصول/دسته‌ی دیگر **هشدار** می‌دهد (بخش ۱۰.۲).
- صفحه‌ی اصلی و دسته‌ی «باقلوا» عمداً روی نیت‌های متفاوت تنظیم شده‌اند (جدول ۲.۱).

### ۱.۳ نام برند
نام برند فقط **یک‌جا** تعریف می‌شود: `Setting` با کلید `seo.brandName` (پیش‌فرض: `علی حان`).
- عنوان همه‌ی صفحات، schema و متن‌های پیش‌فرض از همین مقدار می‌خوانند.
- املاهای دیگر (`علیحان`، `علی‌حان`، `Alihan`، `ALIHAN`) فقط در `alternateName` در schema سازمان می‌آیند تا گوگل همه را به یک برند وصل کند. در متن صفحات املاهای مختلف قاطی نشوند.

## 3. ریسک‌های سئوی مخصوص این پروژه (ایران / Next.js)

این موارد در سایت‌های معمولی مطرح نیستند ولی اینجا اگر رعایت نشوند، سئو عملاً صفر می‌شود:

| # | ریسک | قاعده |
|---|---|---|
| ۱ | **سرور ایران و دسترسی Googlebot** — Googlebot از IPهای خارج از ایران می‌خزد. اگر فایروال/CDN (مثلاً آروان) ترافیک خارجی را ببندد یا چالش JS/captcha نشان دهد، صفحات از ایندکس خارج می‌شوند. | در `DEPLOYMENT.md` صریح نوشته شود: ترافیک خارجی **نباید** geo-block شود و Googlebot نباید به چالش بخورد. تست: `curl -A "Googlebot" https://domain/` از یک سرور خارج از ایران باید 200 و HTML کامل برگرداند. |
| ۲ | **واحد پول در schema** — تومان کد ISO ندارد. | در structured data: `priceCurrency: "IRR"` و `price = قیمت تومان × 10`. تست واحد اجباری. |
| ۳ | **تصاویر OG با متن فارسی** — `next/og` (Satori) در شکل‌دهی حروف فارسی/RTL قابل اتکا نیست. | تصویر OG را **با متن به‌صورت پویا تولید نکن**. از عکس خود محصول (برش ۱۲۰۰×۶۳۰ با `sharp` هنگام آپلود) استفاده کن. |
| ۴ | **نرمال‌سازی فارسی** — «پسته ای» / «پسته‌ای»، «ي/ی»، «ك/ک». | متن صفحات با املای درست (نیم‌فاصله، ی و ک فارسی). تحلیلگر سئوی ادمین هنگام مقایسه همه را نرمال کند (بخش ۱۰.۲). **هیچ‌وقت** املاهای غلط برای «پوشش» در متن تکرار نشود. |
| ۵ | **محتوای مخفی در accordion** — در طرح، «توضیحات محصول» جمع‌شونده است. | متن کامل باید در HTML اولیه باشد (با `<details>` یا CSS)؛ **نه** اینکه با کلیک fetch یا render شود. |
| ۶ | **ایندکس موبایل‌محور** — گوگل نسخه‌ی موبایل را ایندکس می‌کند. طرح موبایل صفحه‌ی اصلی بخش‌هایی از دسکتاپ را ندارد. | یک HTML واحد responsive. **ممنوع**: تشخیص دستگاه با user-agent یا رندر شرطی که محتوای متنی را در موبایل حذف کند. تمام متن سئوی دسکتاپ در موبایل هم در DOM باشد. |
| ۷ | **H1 تکراری** — هیرو دسکتاپ و موبایل طراحی متفاوت دارند. | اگر دو نسخه‌ی هیرو در DOM است، فقط **یکی** H1 دارد. در کل صفحه دقیقاً یک `<h1>`. |
| ۸ | **امتیاز ستاره‌ای در طرح** — طرح «۵ ستاره (۱۳۳ نظر)» نشان می‌دهد ولی نسخه ۱ سیستم نظر ندارد. | در v1 ستاره و تعداد نظر **نه در UI و نه در schema**. داده‌ی ساختگی در schema می‌تواند به جریمه‌ی دستی گوگل منجر شود. |
| ۹ | **ایندکس شدن سرور تست (staging)** یا **برعکس، انتشار production با noindex** | کنترل با متغیر محیطی `ALLOW_INDEXING` (بخش ۸.۳) + چک‌لیست انتشار. |

## 4. ساختار URL و قواعد canonical

### ۴.۱ الگوی URL
| نوع | الگو | نکته |
|---|---|---|
| صفحه‌ی اصلی | `/` | |
| محصول | `/products/{slug}` | **تخت** — دسته در URL نمی‌آید تا جابه‌جایی دسته URL را نشکند |
| دسته | `/category/{slug}` | زیردسته هم تخت |
| همه‌ی محصولات | `/products` | |
| شعبه‌ها | `/branches` و `/branches/{slug}` | |
| صفحات ثابت | `/about`، `/contact`، `/faq`، `/shipping`، `/returns`، `/privacy` | از مدل `Page` |
| جستجو | `/search?q=` | `noindex, follow` |

### ۴.۲ قواعد
- نامک فقط: حروف کوچک لاتین، عدد، خط تیره. حداکثر ۶۰ کاراکتر. بدون حروف فارسی.
- `trailingSlash: false` در `next.config.ts` (Next خودش `/x/` را به `/x` ریدایرکت می‌کند).
- یک دامنه‌ی canonical (پیش‌فرض بدون www، HTTPS). نسخه‌ی دیگر در Nginx با 301 ریدایرکت شود — در `DEPLOYMENT.md`.
- همه‌ی canonicalها **مطلق** و از `NEXT_PUBLIC_SITE_URL` ساخته شوند.
- پارامترهای مرتب‌سازی/فیلتر (`?sort=`، `?category=`) → canonical به URL تمیز بدون پارامتر.
- صفحه‌بندی: `?page=2` به **خودش** canonical شود (نه به صفحه‌ی ۱). صفحه‌ی ۱ هرگز `?page=1` نداشته باشد.
- پارامترهای ناشناخته (`utm_*`، `fbclid`) هیچ‌وقت در canonical نیایند.

### ۴.۳ رفتار محصول غیرفعال / حذف‌شده — 🔴 جایگزین بخشی از بند ۷.۱ ARCHITECTURE
در `ARCHITECTURE.md` محصول غیرفعال از سایت پنهان می‌شود. از نظر سئو اگر یک محصول فصلی چند هفته غیرفعال شود و 404 بدهد، رتبه‌اش از دست می‌رود و برگشتنش ماه‌ها طول می‌کشد. بنابراین:

| وضعیت | لیست‌ها و جستجو | صفحه‌ی محصول | sitemap | schema |
|---|---|---|---|---|
| `isActive = true` | نمایش | 200، قابل خرید | ✅ | `InStock` |
| `isActive = false` | **پنهان** | **200**، با پیام «در حال حاضر قابل سفارش نیست» + دکمه‌ی خرید غیرفعال + محصولات مرتبط | ✅ | `OutOfStock` |
| بایگانی‌شده (`archivedAt` پر) | پنهان | **301** به مقصد انتخابی ادمین (پیش‌فرض: دسته‌ی والد) | ❌ | — |

> این **مدیریت موجودی نیست** — هیچ شمارنده یا محاسبه‌ای اضافه نمی‌شود. فقط نمایش همان کلید `isActive` در صفحه‌ی محصول تغییر می‌کند. رفتار سبد خرید (حذف آیتم غیرفعال) طبق `ARCHITECTURE.md` بدون تغییر.

## 5. قواعد رندر صفحات

### ۵.۱ Metadata
- فقط با `generateMetadata` و builderهای `src/lib/seo/metadata.ts`:
  `buildHomeMetadata()`، `buildProductMetadata()`، `buildCategoryMetadata()`، `buildPageMetadata()`، `buildBranchMetadata()`.
- Layout ریشه: `metadataBase` از `NEXT_PUBLIC_SITE_URL` و `title.template = "%s | {brandName}"`.
- صفحه‌ی اصلی: `title.absolute`.
- اولویت مقدار: `seoTitle` ← اگر خالی: `name`. متا: `metaDescription` ← اگر خالی: ۱۵۵ کاراکتر اول توضیحات بدون HTML، بریده‌شده روی مرز کلمه.
- هر صفحه: `alternates.canonical`، `openGraph` (type، title، description، url، `locale: "fa_IR"`، siteName، images)، `twitter` (`summary_large_image`)، `robots`.
- `<html lang="fa-IR" dir="rtl">`.
- هیچ `<meta name="keywords">` — گوگل از آن استفاده نمی‌کند و `focusKeyword` فقط داده‌ی داخلی ادمین است.

### ۵.۲ ساختار سرتیترها
| صفحه | H1 | H2ها |
|---|---|---|
| اصلی | `خرید باقلوای ترکی {brandName}` (از `Setting`) | محصولات پرطرفدار، داستان علی حان، و H2های بلوک محتوای سئو |
| محصول | نام محصول (`name`) | توضیحات محصول، سوالات متداول (در صورت وجود)، محصولات مرتبط |
| دسته | `name` دسته | بخش‌های `bottomContent` |

**نکته‌ی طرح صفحه‌ی اصلی:** شعار بزرگ «طعم اصالت در هر لقمه» H1 **نیست** — یک `<p>` با استایل تیتر است. H1 همان متن کوچک بالای شعار (eyebrow) است که از «باقلواهای لوکس ترکی» به `خرید باقلوای ترکی علی حان` تغییر می‌کند. ظاهر بصری طرح حفظ می‌شود. در کاروسل هیرو فقط اسلاید اول H1 دارد؛ متن اسلایدهای بعدی تیتر نیست.

### ۵.۳ رندر سمت سرور
- صفحات محصول، دسته، اصلی، شعبه و صفحات ثابت: **Server Component** با محتوای کامل در HTML اولیه.
- نام، قیمت، توضیحات، breadcrumb و لینک‌های داخلی هرگز فقط سمت کلاینت رندر نشوند.
- `notFound()` برای slug ناموجود ← وضعیت واقعی 404 (نه صفحه‌ی 200 با متن «پیدا نشد»).

### ۵.۴ محتوای صفحه‌ی اصلی
طرح صفحه‌ی اصلی تقریباً فقط تصویر است؛ برای رتبه گرفتن در «خرید باقلوا» و «باقلوای ترکی» متن لازم است:
- یک **بلوک محتوای سئو** قبل از فوتر، قابل مشاهده (نه پنهان)، ۴۰۰ تا ۷۰۰ کلمه، با H2 و لینک‌های داخلی به محصولات. پیش‌نویس در بخش ۱۴.
- یک **بلوک سوالات متداول** (۵ تا ۸ سوال) زیر آن.
- هر دو از پنل ادمین قابل ویرایش (`Setting`: `seo.home.content`، `seo.home.faq`).
- طراحی بلوک متنی با تم تیره‌ی سایت هماهنگ و خوانا باشد؛ می‌تواند با «ادامه‌ی مطلب» کوتاه شود **به شرط** اینکه کل متن در DOM باشد.

## 8. Sitemap، Robots و کنترل ایندکس

### ۸.۱ `app/sitemap.ts`
- پویا از دیتابیس. شامل: صفحه‌ی اصلی، `/products`، دسته‌های بدون noindex، محصولات بایگانی‌نشده و بدون noindex (فعال **و** غیرفعال)، شعبه‌های فعال، صفحات منتشرشده‌ی بدون noindex.
- `lastModified` از `updatedAt` واقعی. `changefreq` و `priority` لازم نیست (گوگل نادیده می‌گیرد).
- آدرس‌ها مطلق.
- ساختار اجازه دهد در آینده با `generateSitemaps` چندتکه شود (فعلاً لازم نیست).

### ۸.۲ `app/robots.ts`
```
User-agent: *
Allow: /
Disallow: /admin
Disallow: /account
Disallow: /cart
Disallow: /checkout
Disallow: /login
Disallow: /api/
Sitemap: https://domain/sitemap.xml
```
- `/search` در robots بسته **نشود** — با متای `noindex, follow` کنترل می‌شود (اگر بسته شود، گوگل متای noindex را نمی‌بیند).
- مسیر سرو رسیدها هدر `X-Robots-Tag: noindex, nofollow` داشته باشد.

### ۸.۳ کنترل محیط
متغیر محیطی جدید:
```env
ALLOW_INDEXING=false     # فقط روی production واقعی: true
```
- `false` ← `robots.txt` برابر `Disallow: /` **و** همه‌ی صفحات متای `noindex, nofollow`.
- `true` ← رفتار عادی.
- در پنل ادمین، اگر مقدار `false` باشد و دامنه برابر `NEXT_PUBLIC_SITE_URL` production است، یک **بنر قرمز هشدار** در بالای داشبورد نمایش داده شود («سایت برای گوگل بسته است»).

### ۸.۴ Search Console
- تأیید مالکیت با متای `google-site-verification` از `Setting` (بدون اسکریپت خارجی). همین برای Bing.
- هیچ اسکریپت آنالیتیکس خارجی در v1 اضافه نشود مگر با تأیید (طبق قانون «بدون درخواست خارجی» در `ARCHITECTURE.md`).

## 10. پنل مدیریت

### ۱۰.۱ فرم محصول و دسته — تب/بخش «سئو»
- فیلدهای بخش ۶ با شمارنده‌ی کاراکتر زنده.
- **پیش‌نمایش نتیجه‌ی گوگل** (SERP preview): عنوان کامل با قالب برند، URL به شکل breadcrumb، متا. برش بصری عنوان حدود ۶۰ و متا حدود ۱۶۰ کاراکتر.
- ویرایش slug با هشدار: «تغییر نامک، ریدایرکت خودکار از آدرس قبلی می‌سازد.»
- دکمه‌ی «تولید متای پیش‌فرض» که از توضیحات برش می‌زند (کاربر تأیید کند).
- ویرایشگر FAQ (افزودن/حذف/ترتیب سوال و جواب).
- در فرم تصاویر: فیلد alt کنار هر تصویر، الزامی.
- **حذف محصول** ← به «بایگانی» تبدیل می‌شود و فرم انتخاب مقصد ریدایرکت (پیش‌فرض دسته‌ی والد) باز می‌شود.

### ۱۰.۲ تحلیلگر سئو (جایگزین Yoast)
تابع خالص `src/lib/seo/analyze.ts` با تست واحد؛ همان تابع در فرم (کلاینت) و در سرور استفاده شود. خروجی: لیست چک‌ها با وضعیت 🟢/🟠/🔴 و پیام فارسی. **فقط هشدار است — هیچ‌وقت ذخیره را مسدود نکند.**

| چک | 🟢 | 🟠 / 🔴 |
|---|---|---|
| طول عنوان کامل (با برند) | ۳۰ تا ۶۵ کاراکتر | خارج از بازه |
| طول متا | ۱۱۰ تا ۱۶۰ | خارج از بازه یا خالی |
| کلمه‌ی کانونی در عنوان سئو | هست | نیست |
| کلمه‌ی کانونی در H1 (نام) | هست | نیست |
| کلمه‌ی کانونی در متا | هست | نیست |
| کلمه‌ی کانونی در ۱۰۰ کلمه‌ی اول توضیحات | هست | نیست |
| تعداد کلمات توضیحات | ≥ ۲۵۰ | کمتر |
| همه‌ی تصاویر alt دارند | بله | خیر |
| تصویر اصلی تعیین شده | بله | خیر |
| لینک داخلی در توضیحات | ≥ ۱ | ۰ |
| **کلمه‌ی کانونی تکراری** در محصول/دسته‌ی دیگر (کوئری سرور) | یکتا | 🔴 تکراری + نام صفحه‌ی رقیب |
| **عنوان سئو یا متای تکراری** در سایت (کوئری سرور) | یکتا | 🔴 تکراری |
| تکرار بیش از حد کلمه‌ی کانونی | ≤ ۶ بار در ۳۰۰ کلمه | بیشتر (پر کردن کلمه) |
| صفحه noindex است | — | 🔴 هشدار برجسته |

**نرمال‌سازی قبل از مقایسه** (`normalizeFa()` در `src/lib/seo/text.ts`): تبدیل `ي`→`ی` و `ك`→`ک`، نیم‌فاصله و فاصله‌های متوالی ← یک فاصله، حذف اعراب و تطویل، حروف لاتین کوچک. بنابراین «باقلوا پسته ای» و «باقلوا پسته‌ای» یکی شمرده شوند.

در لیست محصولات ادمین یک ستون «وضعیت سئو» (دایره‌ی رنگی بر اساس تعداد 🔴 و 🟠) باشد.

### ۱۰.۳ صفحه‌ی «ریدایرکت‌ها»
- CRUD ریدایرکت (از، به، 301/410، یادداشت، فعال).
- **ورود گروهی از CSV** (ستون‌ها: `from,to,status`) — برای نقشه‌ی مهاجرت از وردپرس.
- نمایش تعداد استفاده و آخرین استفاده.
- اعتبارسنجی: جلوگیری از حلقه (A→B→A) و زنجیره‌ی بیش از یک پرش (اگر B خودش ریدایرکت دارد، هشدار و پیشنهاد مقصد نهایی).

### ۱۰.۴ صفحه‌ی «خطاهای 404»
- لیست `NotFoundLog` مرتب‌شده بر اساس تعداد، با دکمه‌ی «ساخت ریدایرکت» کنار هر ردیف.
- مسیرهای بی‌ارزش (`/wp-login.php`، `.env`، الگوهای اسکنرها) لاگ نشوند.

کلیدهای `seo.*`، `org.*` و `verification.*` از بخش ۶.۵، شامل ویرایشگر محتوای سئو و FAQ صفحه‌ی اصلی.

## 11. ریدایرکت‌ها و مهاجرت از وردپرس

> 🔴 **بزرگ‌ترین ریسک سئوی کل پروژه.** اگر سایت جدید روی همان دامنه بالا بیاید و آدرس‌های قدیمی ووکامرس 404 بدهند، هر رتبه و بک‌لینکی که سایت قبلی داشته از دست می‌رود. «مهاجرت داده نداریم» درباره‌ی دیتابیس است، نه آدرس‌ها.

### ۱۱.۱ پیاده‌سازی
- مسیر catch-all: `src/app/(shop)/[...legacy]/page.tsx` (کمترین اولویت مسیریابی):
  1. مسیر را decode و نرمال کن (حذف اسلش انتهایی، decode درصدی برای slugهای فارسی قدیمی، یکسان‌سازی حروف).
  2. در جدول `Redirect` جستجو ← اگر 301: `permanentRedirect(toPath)`؛ اگر 410: پاسخ 410.
  3. قواعد الگویی پیش‌فرض (پایین).
  4. در غیر این صورت: ثبت در `NotFoundLog` و `notFound()`.
- در صفحات محصول/دسته/شعبه/صفحه: اگر slug پیدا نشد، قبل از 404 در `SlugHistory` جستجو ← `permanentRedirect` به slug فعلی.
- کش درون‌حافظه‌ای جدول Redirect با TTL کوتاه (مثلاً ۶۰ ثانیه) که هنگام ویرایش در ادمین پاک شود.
- ⚠️ `permanentRedirect` در Next کد 308 برمی‌گرداند؛ گوگل 308 را مثل 301 دائمی حساب می‌کند.
- ⚠️ پاسخ 410 از یک page component مستقیم ممکن نیست؛ برای 410 از route handler یا middleware با `matcher` محدود به مسیرهای قدیمی استفاده کن و راه‌حل انتخابی را در گزارش فاز توضیح بده.

### ۱۱.۲ قواعد الگویی پیش‌فرض ووکامرس (فقط وقتی ردیف دقیق در جدول نیست)
| الگوی قدیمی | مقصد |
|---|---|
| `/shop` ، `/shop/*` | `/products` |
| `/product/{x}` | `/products` + ثبت در 404-log برای نگاشت دستی |
| `/product-category/{x}` | `/products` + ثبت در لاگ |
| `/cart` ، `/checkout` ، `/my-account/*` | معادل‌های جدید (`/cart`، `/checkout`، `/account`) |
| `/sitemap_index.xml` ، `/*-sitemap.xml` (Yoast) | `/sitemap.xml` |
| `/feed` ، `/*/feed` ، `/wp-json/*` ، `/xmlrpc.php` | 410 |
| `/?add-to-cart=*` ، `/?p=*` | `/` |
| `/wp-content/uploads/*` | 410 (مگر ادمین برای تصاویر مهم ریدایرکت دستی بسازد) |

> ریدایرکت نرم به `/products` فقط برای جلوگیری از گم شدن کاربر است؛ هدف اصلی نگاشت دقیق هر URL قدیمی به صفحه‌ی معادل است (بخش ۱۱.۳).

### ۱۱.۳ نقشه‌ی مهاجرت
1. کارفرما فهرست URLهای قدیمی را از **Search Console سایت قبلی** (گزارش Pages و Performance → خروجی) و در صورت امکان sitemap قدیمی Yoast تهیه می‌کند و در `docs/legacy-urls.csv` می‌گذارد.
2. Claude Code اسکریپت `npm run seo:map-legacy -- docs/legacy-urls.csv` بنویسد که:
   - هر URL قدیمی را نرمال و decode کند،
   - با مقایسه‌ی `normalizeFa` نام/slug فارسی قدیمی با نام محصولات و دسته‌های جدید، **پیشنهاد** مقصد بدهد،
   - خروجی `legacy-redirects.csv` با ستون‌های `from,to,status,confidence` بسازد.
3. کارفرما فایل را بازبینی و از صفحه‌ی ریدایرکت‌ها import می‌کند.
4. پس از انتشار، صفحه‌ی 404ها تا یک ماه مرتب بررسی شود.

## 12. لینک‌سازی داخلی

- **Breadcrumb** قابل مشاهده در صفحه‌ی محصول و دسته: خانه › باقلوا › باقلوا گردویی (همراه `BreadcrumbList`).
- **محصولات مرتبط** در صفحه‌ی محصول: ۴ محصول فعال از همان دسته، سپس دسته‌ی والد.
- دسته‌ی هاویج: لینک از صفحه‌ی ۴ محصول هاویج به hub و برعکس.
- **بلوک محتوای صفحه‌ی اصلی**: لینک با متن دقیق نام محصول (مثلاً «باقلوا گردویی» ← `/products/baklava-gerdouyi`).
- **فوتر**: ستون «دسترسی سریع» + لینک به دسته‌های اصلی. لیست بلند کلمه‌ی کلیدی در فوتر ممنوع.
- دایره‌های دسته‌بندی صفحه‌ی اصلی (طرح موبایل) لینک واقعی `<a href>` باشند، نه دکمه‌ی JS.
- همه‌ی لینک‌های داخلی `<Link href>` با آدرس واقعی — ناوبری فقط با `onClick` ممنوع.
